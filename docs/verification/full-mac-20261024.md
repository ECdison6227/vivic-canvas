# Mac mini 原生验收记录

2026-10-24。本记录仅陈述真实执行结果。目标为用户提供的 Mac mini；不覆盖已有 App、服务或 SSH 配置，不发布、不推送。自动化不采集物理麦克风/摄像头，不播放声音。

## SSH 交接与初始阻塞（后续已恢复）

- 已在执行机建立独立 `~/.ssh/vivic-mac-mini.conf` 和 `~/.ssh/vivic_macmini_known_hosts`；建立前确认它们不存在，使用 UTF-8 无 BOM。已有私钥只被 OpenSSH 使用，未输出或复制。
- 两跳均要求 Ed25519、指定公钥、`IdentitiesOnly yes`、`StrictHostKeyChecking yes`、禁用 agent forwarding。Mac 预期指纹与用户交接相符：`SHA256:8Tv+4DsLO+FqXGGc20gmD7goudYAaQ4hKMJBFrP0LMI`。
- 中继主机指纹校验通过，公钥认证成功。受限跳板账号不允许执行普通远程命令，未尝试绕过。
- 多次实际连接（包括用户回复恢复后的 20 秒重试）停在 SSH banner：`Connection timed out during banner exchange` / `Connection to UNKNOWN port 65535 timed out`。
- 另外直接运行 `ssh -vv ... -W 127.0.0.1:22223 vivic-ssh-relay` 排除了 ProxyJump 配置传播问题：日志明确 `Authenticated ... using publickey` 与 `channel 0: open confirm rwindow 2097152 rmax 32768`，12 秒内 banner 仍为空。

该阶段只证明中继认证及转发通道可建立，尚不能证明 Mac sshd 可达；当时没有把交接预期当成系统实测。

交给用户本地 Agent 的最短定位：

```sh
# Mac 本机：应该迅速出现 SSH-2.0 banner。
nc -G 3 -w 3 127.0.0.1 22 </dev/null
lsof -nP -iTCP:22 -sTCP:LISTEN

# 中继上有权限的维护会话，只读检查。
ss -lntp 'sport = :22223'
timeout 3 nc 127.0.0.1 22223 </dev/null
```

若本机 22 正常而中继 22223 无 banner，需要检查实际占据 22223 的反向隧道。仅新建连接可能因为旧隧道占据端口而失败。既有跳板限制与主机校验保持不变。

- Node 官方站在 Mac 上直接下载很慢，改为经严格 SSH 传送相同已校验官方压缩档；模型也使用已校验缓存迁移后再由 Mac prepare 重验，不能将此当作 Mac 首次公网全量下载体验通过。

本轮没有把 Windows 的 Node、llama 引擎、Python 或 node_modules 拷到 Mac 冒充原生依赖。

## 原生构建与安装验收

忽略缓存 `.cache/mac-acceptance-20261024/` 保存筛选后的源码/正式 APK、隔离 bootstrap 与证据；不含私钥、用户连接设置或模型凭据。pnpm 12.11.2 已在 Mac 按锁安装 790 个包，原生 Web build/API deploy 成功；交付包内的 sharp/esbuild 用内置 arm64 Node 实际执行通过。

补强 `scripts/package-macos-smoke.mjs`，原先只验证 App 复制与 plist 的环节现在会实际运行安装后 `Contents/MacOS/Vivic`：

1. 使用含空格的独立 `.app` 路径，验证本安装拥有自己的 API 进程。
2. 校验 health，以及 `/`、`/launcher`、`/display`、`/mobile` 四个本地 HTML 入口。
3. 下载随桌面包提供的 Android APK，核对 metadata 大小及 SHA256。
4. 从安装路径停止服务并确认端口关闭。
5. 保留占用端口不干扰、重复启动、禁止覆盖安装、不复制凭据/运行状态、伪造 PID 不终止其它进程等原有检查。

实际安装还发现 Node `fs.cp` 默认把 12 个 `.bin` 相对 symlink 变成指向解压目录的绝对路径。已用 `verbatimSymlinks: true` 修复，新增逐个检查安装后链接必须仍解析在 App 内的断言，避免用户删除解压目录后工具入口损坏。修复前审计留在 `install-link-audit-initial.json`。

最终增强烟测 **15 项通过**，包含上面安装/链接/HTML/APK/进程隔离检查。脚本语法和差异检查通过；既有 runtime 三文件 **20 测试在 Windows 和实际 Mac 分别通过**。最终 ZIP 在烟测启动任何服务前已封装，没有将运行状态或临时 token 再打回交付包。取回后逐项核对锁文件、Mac 安装器和内置正式 APK 与本轮源文件 SHA 相符，包内没有 `.env`、`.launcher.json` 或运行日志。

## Mac 模型与本地语音

首次 prepare 在 Python 锁安装失败，实际原因是 `sherpa-onnx-core` 被错误限定为 Windows。官方 [sherpa-onnx-core 1.12.32](https://pypi.org/project/sherpa-onnx-core/1.12.32/) 提供 Mac arm64/x64/universal2 wheels，且是 `sherpa-onnx` 的依赖。现有锁已经包含这些 SHA；修复仅去除错误平台 marker，未放宽 hash 校验。失败记录保留在 `native-initial-failure.json`。

修复后独立 uv/CPython 3.12.15 环境实际安装成功。Windows 另外准备了 39 个匹配 Mac tags、每个均在锁中核验 SHA 的备选 wheel，但本次 Mac uv 已直接完成安装，成功结果没有使用备选 wheelhouse 安装。首次模型准备使用迁移后的已验证权重与原生引擎档，Mac 再完整校验。

| 0.8B「展开这张便笺」 | accepted/expand，约 420 ms |

4B 首次被 Node `os.freemem()` 的低值拒绝，记录仍保留。OS 查询显示大量 inactive/file-backed 页可回收，`memory_pressure -Q` 为 86% free、swap 为 0。验收脚本现对 Mac 使用 `vm_stat` 的 **free + inactive + speculative** 估计，封顶总内存、不重复加 purgeable，失败回落 Node 低值；保留两种原始数据和来源。4B 的 8 GiB 门槛不变；真正加载前估计可用 **11.65 GiB**，Node 原始 free 为 **0.57 GiB**。运行前后压力仍为 86% free，swap 为 0。该调整仅用于验收脚本，产品 profile 推荐仍使用原有保守 Node 指标。

`verify-local-runtime.mjs` 新增严格四档 `--profile` 和明确不运行推理的 `--prepare-only`；默认仍为 0.8B。Windows 也成功完成推荐 4B 的完整固定缓存准备，但因当时可用内存约 0.94–5.09 GiB，未在 Windows 强行加载；Windows 不冒领 Mac 推理结果。

## 4B 原生 v2 质量边界

又以 8,192 context 跑了真实 `native-v2-probe.ts`，只在独立内存任务中使用合成画布，任何 execution receipt 均明确模拟，不操作用户画布：

- 短 baseline：946 ms。
- 五条完整任务 **5/5 返回有效 native 概率**，每次约 **14.05–14.24 秒**。
- **0/5 形成通过现有门控的原生执行**，全部交回探针的占位 LLM。探针故意不连接云 LLM，因此其 final unknown/failed 不等于线上完整服务调用失败。
- 该结果证明 4B 原生推理可以运行，不能证明正式 Jev v2 质量或速度达标。正式特调权重、校准、端到端性能仍需后续验收；默认执行门控未开启、阈值未降低。
