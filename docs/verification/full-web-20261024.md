### 既有公网 relay 补验

用户已授权全量测试，检查发现本机已有有效的私有 relay 配置，因此不再仅因默认 opt-in 将此项略过。只在进程内使用既有 secret，未打印或复制其内容。

首次使用新隔离端口 `17874` 时，既有中继按 Origin 白名单拒绝 WebSocket 升级（HTTP 403）；公开手机页为 HTTP 200，配置内授权 Origin 和既有 `localhost:5174` 均可升级。证据为 `private-relay-availability.json`。随后确认 `5174` 空闲，使用该原已授权测试端口，API 仍为独立 `17878`，**没有修改服务器白名单、部署或用户原服务**。

`VIVIC_LIVE_MOBILE=1` 场景 **1/1 通过**（11.6 秒业务场景，含启动 25.7 秒）：真实生成一次性二维码 → 通过已部署手机页 fragment 配对并清除 fragment → 同步已有卡片正文 → 手机固定、电脑 Display 同步 → 手机新建便笺并等待 owner 保存 → Display 重载仍存在 → 手机看到新正文 → 切换画布同步 → 撤销授权与停止连接。手机不创建 owner 或 IndexedDB。该项使用手机尺寸浏览器和链接配对；原生相机扫描另见 Android 验收，不混为同一种证据。

日志/JSON/截图在 `private-relay-allowed.*` 与 `private-relay-allowed/`，首轮 Origin 拒绝证据保留于 `private-relay.*`。测试新增了实际自建 desktop/mobile context 的静音和物理采集禁用初始化。结束后 `5174 / 17874 / 17878 / 45989 / 18794` 均无本任务监听服务。

## 稳定性与 Browser Extension

当前问题应优先在页面自身的 owner、保存回执、重连与弹层上修复。现有代码已有 Web Locks/heartbeat 单 owner、IndexedDB 持久化、版本缺口/owner epoch 的完整快照恢复、重复请求保护。浏览器扩展不会自动替代这些机制。

本轮用正常后台节流参数测试“先建卡，再通过展示窗口按钮打开 popup”，以及冻结/恢复后的快照补齐，**通过**；owner 关闭后重开、Display 重载、二个 owner 争用/接管、离线本地降级也通过。真实 Chrome computer-use 中个别 popup 激活/截图超时的现象没有在这些正常浏览器用例复现；直接打开同一 URL 的原卡数据仍正常。未为了 CUA 的特定窗口控制限制修改 React Flow。

**本轮不需要添加 Browser Extension。** 受测稳定性问题已经在现有应用内修正；增加扩展没有被当前证据证明能解决额外问题。后续如明确需要跨站采集或浏览器关闭后后台执行，再为该具体能力单独设计。

手机是桌面会话的配对遥控。浏览器关闭、系统休眠或电脑离线后持续后台运行属于后台会话/服务的另一个能力；不把安装扩展当作这个能力已经实现。
