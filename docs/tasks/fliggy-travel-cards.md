## 用户结果

用户描述旅游需求，Vivic 查询飞猪相关服务，将可核实的结果整理成旅游卡片；用户可以查看、比较、选择，并通过实际提供的链接查看详情。首个可交付查询场景先在下面的能力核对中选定，再逐步扩展为系列。

酒店、交通、景点/玩法、行程摘要都是候选分类，不是本次已批准的固定卡片清单。可以复用现有比较/日程卡，也可以新增专用类型；由数据形状、交互和已有卡片能否表达决定，不为每个接口机械新增一种卡片。

首版以查询与展示为建议边界。查到可预订信息/详情链接不等于已有订单创建与支付能力；交易和修改预订要另写明确任务，不夹带在卡片展示中。

## 第一份交付：固定接入与卡片协议

由负责接入的人核对选定官方服务/版本，交付 `docs/cards/fliggy/spec.md`，至少写清：

| 必须明确的项目 | 需要记录的事实 |
| --- | --- |
| 服务身份 | 官方文档、选定版本、实际 endpoint/传输、鉴权方式；只写凭据引用，不写 Key |
| 工具能力 | 实际工具名和输入 Schema、响应样例/错误；不能把 CLI 子命令名猜成 MCP 工具名 |
| 字段来源 | 原始字段 → 内部字段的逐项映射、可空/必填、单位/币种/日期时区、是否可能缺失 |
| 卡片用途 | 每种卡片触发意图、复用或新增类型理由、scene/cardType 名称及尺寸候选 |
| 生命周期 | 加载、成功、空结果、错误、取消、刷新和过期；哪些只在内存，哪些可持久化 |
| 编辑和动作 | User 可做什么、Display 只展示什么；选择/筛选/查看详情如何进入宿主 |
| 并行接口 | 前端固定 props/事件；后端适配器固定输入/输出；样例和共享集成文件的负责人 |
| 验收 | 用户原话、有效样例、错误样例、真实请求证据与尚未覆盖项 |

下列是**Vivic 内部字段设计时的考虑项，不是飞猪现成接口**：查询条件、结果 ID/标题、由上游提供的价格与币种、有效日期、来源链接、获取时间、演示标记。最终字段名称和限制由 spec 与对应 Zod Schema 固定；未知值保持缺失/未知，不自动显示成 0 元、有票或已预订。

以酒店查询卡为设计例子（不是已选定的首卡）：

| 参数/数据 | 编辑建议 | 修改后的行为 |
| --- | --- | --- |
| 目的地、入住/离店日期、预算 | 用户可改，字段是否支持须与真实服务核对 | 校验后重新查询；新条件不覆盖到旧结果标签上 |
| 排序、显示条数 | 支持的枚举/范围内可改 | 已取回数据能完成的本地重排即可；仅能服务端排序时重新查询 |
| 价格、库存、服务评分、获取时间 | 普通用户参数编辑只读 | 只由真实结果更新；不能手改后仍显示为飞猪事实 |
| 收藏/选中结果、用户备注 | 用户可改 | 保存到实例用户状态；刷新时保留，失效项单独处理 |

前端外观先给出视图结构：标题/查询摘要、核心结果列表、价格与来源、User 参数编辑区。优先评估现有 ComparisonCard、列表/图片部件和 SceneCardShell，信息与动作契约符合才直接复用。主题跟随宿主的语义变量，不为每张旅游卡另起一套深浅色；验收覆盖两个模式与 12 个背景配色。

若服务接口暂时无法核对，写清未确认项；前端仍可用明确标注的 DEMO fixture 开发独立预览。不要伪造“飞猪真实响应”，也不要把渲染通过写成在线接入通过。

## 系列卡片的验收条件

- [ ] 确认首个查询场景、真实服务能力与输入输出，spec 和 Schema 一致。
- [ ] 正常、无结果、字段缺失、非法价格/日期、错误响应、超时/取消均按约定处理。
- [ ] 展示字段可追溯到用户输入、实际服务结果或明确的确定性计算；不虚构价格、库存、时刻、评分或链接。
- [ ] DEMO 与实际服务结果有明确区别；刷新后不把旧结果当作新查询，显示可核实的获取时间/过期状态。
- [ ] 凭据和不必要的个人信息不进入卡片、前端存储、同步、导出、截图或日志。
- [ ] Display 只读、User 在可写 owner 下操作；操作经过宿主校验，不直接修改 store 或持久化。
- [ ] 参数表逐字段说明可编辑范围、来源和副作用；查询/展示/服务结果/用户状态分清，UI 和宿主都落实只读边界。
- [ ] 复用方案、标题/信息/动作层级与尺寸已确定；浅深两种模式和 12 个背景配色可读，长内容、空/错/过期状态有实际预览。
- [ ] 通过完整 CardRecord/ActionEnvelope，保存/刷新/导入导出正常，新旧卡共存，长内容不覆盖固定卡。
- [ ] 必要单测/类型/契约/构建及浏览器验收有真实记录；未完成的 MCP live 验证单独标注。
