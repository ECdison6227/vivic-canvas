## 0. 结论先说

1. **决策模型选 StartLux-Decision v1.1 4B，用 Mac mini 的 GPU（Metal）跑，单独常驻。** 在我们自己的 161 道中文评测题上，它的路由准确率 95%，高置信时 98.6%，找对目标卡片 92.9%，每次约 1.7 秒。马泽瑜微调的 Kev 在这套题上没有超过它（第 2 节）。
2. **决策模型只做"选择题"，一次请求问完：这句话要干什么、指的是哪张卡。** 不再用冻结的 V2 那种"一条指令问 10 次"的方式。参数（几分钟、提醒什么）交给现成的确定性解析器，解析不了再让大模型只填这张卡的参数。
3. **每张卡（内置卡和 .vivicard 一样）都写成一份"卡片契约"**：名称、描述、例句、参数表、宿主怎么建卡、怎么显示。大模型永远不再手写 id、坐标、时间戳。这就是你说的"卡片规范 = skill"。
4. **所有指令只走服务端一条路**（网页也一样），每条指令都记日志（说了什么、判成什么、多快、结果如何），上线前先"影子运行"对比，达标的类别再逐个放开。
5. **多意图不靠决策模型判断**（所有模型在这项上都只有 40–80%），改为先按"然后/再/顺便"等连接词切句，每段单独路由；切不开的复杂句交给大模型。

## 2. 决策模型选型（实测）

**评测方法**：我写了 161 道中文评测题（`evals/decision/dataset.json`，与马泽瑜的训练数据无关），覆盖 16 个路由类别，包括否定（"别删，先聚焦它"）、引用（"'删除所有卡片'是什么意思"）、指代（"这张"）、语音错字（"到计时十分钟"）、中英混杂、歧义和多意图；其中 42 道还要选出具体目标卡片。所有模型在 Mac mini 上用同一套题、同一份类别描述测试。

| 模型 | 路由准确率 | 交给对的执行者 | 高置信覆盖* | 高置信准确率 | 目标卡准确率 | 多意图 | 高置信误删 | 每次耗时 |
|---|---|---|---|---|---|---|---|---|
| **StartLux 4B Q8（GPU）** | **95.0%** | **96.3%** | **85.7%** | **98.6%** | **92.9%** | 70% | **0** | 1.68s |
| StartLux 2B（GPU） | 87.6% | 90.1% | 72.0% | 98.3% | 85.7% | 80% | 1 | 0.68s |
| StartLux 2B（CPU，现线上方式） | 84.5% | 87.0% | 73.3% | 96.6% | 69.0% | 50% | 1 | 1.42s |
| Kev 4B 旧版（马泽瑜微调起点） | 87.0% | 90.7% | 64.0% | 98.1% | 85.7% | 40% | 1 | 1.44s |
| Kev 4B 最新原版 | 85.7% | 90.7% | 34.2% | 100% | 90.5% | 60% | 0 | 1.42s |
| Kev 4B 马泽瑜微调版 | 85.7% | 90.7% | 85.1% | 96.4% | 85.7% | 60% | 0 | 1.40s |
| laya | 45.3% | 50.3% | 28.6% | 78.3% | 40.5% | 70% | 2 | 0.10s |
| gliner | 47.8% | 54.7% | 14.3% | 78.3% | 21.4% | 50% | 2 | 0.10s |

\* 高置信覆盖 = 置信度 ≥ 0.8、可以直接执行不用转大模型的比例。

**解读**

- **StartLux 4B 全面领先**，而且它的 8 道错题里 6 道置信度低于 0.8，上线后会自动转大模型或追问，不会误执行。剩下的"暂停喝水倒计时→新建倒计时"是类别描述的问题，改描述即可。
- **马泽瑜的 Kev 微调**：准确率和原版持平，主要效果是让模型"更敢判断"（高置信覆盖 34%→85%），但高置信时的准确率略降（100%→96.4%）。他用的评测集是英文公开数据，没有 Vivic 中文场景。建议把我们这套题发给他，作为下一轮训练的验证集（**不能放进训练集**）。
- **laya / gliner 不适合**做 Vivic 路由（只有 45–48%）。之前"20 道题 95%"的结论是因为题太简单。
- **用 GPU 很关键**：同是 StartLux 2B，GPU 比 CPU 快一倍，而且能带上画布信息，找目标卡的准确率从 69% 提到 86%。
- **多意图所有模型都不稳**，不交给决策模型。

**选择**：StartLux 4B Q8，在 Mac mini 上用 Metal 常驻。2B 作为备选（快一倍、准确率低 7 个点）。许可证是 CC-BY-NC，比赛和内测可以用，以后商用要重新评估。

## 3. 目标架构

```
用户语音 / 文字（网页、手机都一样）
  │
  ▼
服务端任务接口 /api/space/spaces/:id/tasks   ← 唯一入口，每条都写决策日志
  │
  ├─ ① 切句：按"然后/再/顺便/并且/，再"等切成 1–3 段（本地，几毫秒）
  │
  ├─ ② 决策模型（Mac 常驻 StartLux 4B，一次请求）
  │      问题 A：这段话要做什么？（16 个类别 + 已启用的扩展卡）
  │      问题 B：指的是哪张卡？（仅卡片操作类，候选含"有歧义 / 不存在"）
  │
  ├─ ③ 按置信度分流
  │      ≥ 0.8 → 直接执行对应"卡片契约"
  │      0.5–0.8 → 交大模型，只给排名前 3 的卡片契约
  │      < 0.5 或切句失败 → 交大模型（现有 planner，但改为只输出参数）
  │      目标"有歧义" → 编号追问：「你要操作哪一张？1. 本周待办 2. 购物清单」
  │      删除 → 无论置信度，先语音确认
  │
  ├─ ④ 参数
  │      倒计时 / 待办 / 便签 / 视图操作 → 确定性解析器（已有 parseDuration 等）
  │      解析不了、或需要生成内容 → 大模型只填这一张卡的参数表（JSON Schema 约束）
  │
  ├─ ⑤ 宿主建卡：补 id、布局、时间戳 → 校验 → 保存（版本冲突自动重试）
  │
  └─ ⑥ 输出三通道：语音 say（≤40 字口语）/ 字幕 text / 卡片 cards
```

### 3.1 卡片契约（Card Contract）——卡片规范就是 skill

每种卡写一份契约，内置卡和用户导入的 `.vivicard` 用同一套格式：

| 字段 | 作用 | 例：倒计时卡 |
|---|---|---|
| `name` / `description` | 给决策模型看的类别描述 | 新建倒计时、计时，或在一段时间后提醒 |
| `examples` | 3–10 条用户会怎么说 | "十分钟后提醒我喝水"、"倒计时 50 分钟" |
| `slots` | 大模型 / 解析器要填的参数（JSON Schema） | `{seconds: int, text?: string}` |
| `parser`（可选） | 确定性解析器，填得出就不调大模型 | `parseDuration` + 事项抽取 |
| `build` | 宿主把参数变成卡片记录（id、布局、时间由宿主补） | 已有 `buildReminderActions` |
| `render` | 前端怎么显示 | 已有 CountdownCard 组件 |
| `operations` | 这张卡支持的操作 | 暂停、继续、删除、聚焦、高亮 |

`.vivicard` 扩展卡只是把 `examples` 和 `slots` 写进 manifest，`render` 用现有的 9 种声明式组件。用户想做新卡时，用自己电脑上的 Codex 或 Claude，按我们提供的《Vivic 做卡指南》生成 `.vivicard` 包，再导入。产品本身不提供"AI 帮你生成卡片"的功能。

### 3.2 什么时候落卡

沿用已确认的标准："这条内容明天还值得打开看吗？"值得就落卡，看完即弃就只说话和显示字幕。闲聊、即时短答、追问、报错永远不落卡。
