## 按依赖程度选任务

| 依赖 | 典型工作 | 如何并行 |
| --- | --- | --- |
| 低 | Landing 内容/交互、现有接口下的独立卡片视图、纯数据转换 | 可直接分给伙伴；不要求等待核心重构完成 |
| 中 | 新卡片类型、需要新数据字段/接口的新功能 | 先约定并固定最小协议和样例，再分别开发；共享注册/契约改动拆为集成 PR |
| 高 | 意图/决策路由、模型认证、Action 执行、owner/同步/持久化、全局状态改造 | 由维护者牵头，伙伴可接已隔离且接口稳定的子模块 |

新卡片不天然属于低依赖：当前宿主使用静态 Schema/registry。伙伴可以先在独立预览中实现视图，最终接入可能仍需契约和注册变更，不能假设外部 Card SDK 已存在。

## 给 AI 的限制写在每张任务单里

开工前，任务必须明确以下内容：

1. 用户结果：做成后用户能做什么，给一条具体操作例子。
2. 允许修改的确切文件/新目录，以及不能顺手修改的共享入口。
3. 固定的输入、输出、props/事件或 API 契约；涉及新字段时先约定兼容方式。
4. 可独立使用的样例/fixture，哪些是演示数据，哪些必须来自真实服务。
5. 验收步骤、必要命令、错误/空状态与兼容要求。
6. 基线提交、负责人、分支与集成点；若有依赖，说明伙伴能先完成哪一部分。

允许实现本任务所需的代码和测试；禁止未经任务说明改其他模块、升级依赖、重写全局样式、移动共享文件或修改 CI/规则。涉及这些内容时先列出具体需要，再由维护者协调范围。不能删必要测试、降低断言或跳过检查来制造通过结果。

## 可作为首轮任务的模板（尚未分配）

### Landing 独立迭代

- 先明确要改的段落、素材、交互和验收截图，再限定具体 `apps/web/src/landing/` 文件。
- 复用现有组件，展示样例明确是 Demo；不顺手修改 User/Control/Display 的共享状态。
- 当前本地 Landing 和线上补丁存在发布来源差异。页面开发与线上发布分开验收，不能直接覆盖已上线的申请流程；是否上线由维护者单独安排。
- 验收覆盖桌面/手机、键盘、减少动效及相关前端检查。

### 一张新卡片

- 先选定卡片用途，再给出数据样例、props/事件、尺寸、空/错状态和具体目录。
- 伙伴完成独立 renderer、预览和必要测试。需要扩充 CardRecord、场景表或 registry 时，列出明确的集成改动，不自行重写核心分发。
- 维护者可以同时继续优化核心流程；卡片完成后按约定接口接入，保存/恢复和操作校验随后按集成任务验收。

### 独立数据适配或新功能模块

- 先明确一个输入输出接口和错误类型，限定新增适配器及测试目录。
- 伙伴用 fixture/替身实现与验证；需要真实服务时按任务明确连接和凭据方式。
- `app.ts`、全局认证、数据库/持久化等共享入口的连接由单独集成步骤处理，不因一个适配器任务扩大到全后端重构。

## 发给伙伴的 AI 指令模板

> 先读 AGENTS.md、README_FIRST.md 和 docs/TEAM_TASKS.md。完成 Issue【链接】。目标【用户结果】；允许修改【文件/目录】；保持兼容的接口【契约】；样例【位置】；验收【步骤和命令】。只实现任务内代码与测试，不擅自改核心流程、全局样式、依赖或其他模块；若发现任务必须跨越约定边界，列清所需改动并等待范围协调，继续不受影响的部分。结束时提供改动文件、实际验证结果、预览方式和未完成的集成点。未明确要求时不推送、不合并、不部署。

## 维护者如何接收

先核对 PR 文件范围和协议兼容，再看实际行为、检查结果和错误状态。可独立合入的内容先验收；核心依赖尚未准备好时保留独立预览或 Draft PR，不阻断其他任务。一个任务一个 PR，避免两个 AI 同时改同一核心文件。
