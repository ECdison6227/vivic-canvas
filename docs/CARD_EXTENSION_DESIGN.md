# 从内置卡片走向用户自定义导入

2026-10-20 设计建议，目标是“用户描述需求 → Agent 按 Skill 制作 → 验证/打包 → 用户导入 → 在 Vivic 使用”。本文件明确目标与实施边界，不代表导入器、SDK 或以下文件格式已实现。

用户已确认具体入口与体验：**设置页导入 → 解析/校验 → Vivic Test Space 弹窗预览/试跑 → 确认安装**。流程、测试隔离与验收见 [Test Space 规格](CARD_TEST_SPACE.md)，首轮拆分见 [GitHub 任务草稿](tasks/card-platform-first-sprint.md)。

## 当前与目标的区别

当前新增内置类型需要编译共享 Schema、scene 映射和 React registry。已有画布 JSON 导入只恢复已认识的卡片实例，不能因此安装新类型。当前 Skill 指导队员改源码，不能让用户仅上传一个 React 文件就获得新能力。

要支持用户导入，需要可安装的卡片定义、按包校验/注册、稳定的宿主接口、预览/验证和实例兼容处理。这些属于本地路线 L05–L07，而非只补一份 Markdown。

## 三个对象分别管理

| 对象 | 包含什么 | 由谁管理 |
| --- | --- | --- |
| CardDefinition / 卡片定义 | 包 ID、版本、用途、参数和数据 Schema、UI、动作、宿主兼容与权限声明 | 开发者/Agent 制作，平台安装校验 |
| CardInstance / 一张卡片 | 定义及版本引用、用户参数、选中/备注、服务数据快照、布局 | 平台按实例保存、撤销、同步 |
| ServiceConnection / 服务连接 | 实际 MCP/API 端点、账号凭据、已授权能力 | 本机后端/宿主管理，卡片只引用允许的能力 |

安装一种酒店卡可以创建多张实例，每张有自己的目的地、日期、筛选与选择；共享代码不等于共享用户状态。更换连接不把凭据写入包或实例。

## 包需要表达的内容（候选目录，尚非已支持格式）

```text
my-card/
  manifest.json          包身份、版本、宿主兼容、渲染方式与能力声明
  config.schema.json     用户可配置的参数、默认值与值域
  data.schema.json       服务/模型输出经标准化后的数据
  state.schema.json      用户选择、收藏和备注等持久状态
  ui.json 或 ui/         受控组件组合，或隔离的自定义界面资源
  actions.json           允许操作及输入输出、触发限制
  examples/              DEMO/TEST 与边界样例
```

字段名、包格式、Schema 子集与版本策略需要由 L05 固定并实现，再写 SDK/打包器。不能仅凭有这些文件就认为包可安装。配置表单的显示顺序、字段标题、编辑控件与“修改是否重新查询”等，也需要明确 UI 元数据和宿主执行规则；JSON Schema 本身不包含所有产品交互语义。

## 两种制作路径

**建议先做受控组件组合。** Agent 输出有限组件目录中的布局与数据绑定：标题、指标、图片、列表、对比、日历、图表、表单等；沿用现有主题和宿主动作，不执行任意表达式。现有 Assistant UI registry 和自有卡片是可复用基础，但公开组件目录、参数表单生成、声明式绑定/动作和包导入仍需实现。

这条路径适合大量信息卡片，也更容易校验、保持深浅色一致、自动预览。目录没有的复杂交互，不能靠任意 HTML/JS 字段偷偷越界。

**复杂交互再支持隔离界面扩展。** 开发 Agent 可生成受支持的 React/HTML/CSS/JS 扩展包，在开发环节构建和验证；导入后由隔离宿主运行，通过版本化消息接口获取数据、主题和有限动作。不得把未知 bundle 直接 `import/eval` 进主页面或交给运行中的 LLM 任意执行。

MCP Apps 已定义工具关联 UI、隔离 iframe 和宿主消息通信，可作为此路径的候选；它不自动提供 Vivic 的卡片安装、布局、持久化、迁移和主题一致性。是否采用需做适配验证。参考 [官方概览](https://modelcontextprotocol.io/extensions/apps/overview)、[AppBridge](https://apps.extensions.modelcontextprotocol.io/api/modules/app-bridge.html)。

## 宿主接口至少覆盖

- 获取经过校验的实例数据、参数、编辑能力和当前模式。
- 请求修改允许的配置/用户状态，宿主复核权限和值域；服务事实有单独更新通道。
- 通过声明的服务连接请求动作，响应校验、取消、超时、查询版本和迟到结果处理统一提供。
- 传递主题语义变量、字体/尺寸约束和减少动态效果偏好，并推送变化。iframe 不会自动继承父页面 CSS，必须通过显式主题桥同步。
- 按需报告尺寸、请求受限宿主交互；不能直接改父画布、读取其他卡片私有数据或拿到凭据。
- 保存格式版本、迁移、缺包占位、禁用/卸载与恢复。UI 报错不能让整个画布失效。

这些能力的真实隔离与边界要由宿主实现和验证，不能把 manifest 的声明当成已生效限制。内置卡也应尽量按同一套主题和动作抽象开发，减少以后迁移成本。

## 验收闭环与建议顺序

1. 固定单卡 spec：可编辑参数、只读结果、用户状态、视觉/主题、动作和持久化。
2. 用现有卡片验证协议并提供参考模板；飞猪项目可并行做 renderer/适配，减少核心耦合。
3. 选定一种渲染路径，做最小导入宿主与命令行验证工具；第一版不必同时支持所有路径。
4. 从仓库之外的干净目录，让 Agent 按 Skill 制作一个包；宿主不改源码/不重新构建，用户导入后可创建多实例。
5. 验证参数编辑、来源、深浅色/双模式、重启恢复、升级/禁用/缺包；非法包不能进入可运行状态。
6. 再把真实 SDK API、受支持的文件结构和打包命令写回 Skill，作为外部开发正式契约。

这轮交接包可以支撑内置卡片开发并为上述路线准备规格；尚不能承诺任意用户需求都能无代码接入。应分别报告“独立预览完成”“源码集成完成”“外部导入完成”，避免把不同阶段混为一项验收。
