# Vivic 做卡指南

把本指南交给用户电脑上的 Codex / Claude，在本机代码目录中制作 `.vivicard` 声明式卡片包。Vivic 负责导入、校验、预览和显示受控 JSON；制作工作使用本机编程工具，不需要在 Vivic 产品中增加编程入口。

本指南的完整示例是 [fitness-log](../../examples/vivicard/fitness-log/manifest.json)，记录训练日期、部位和分钟数。协议依据是仓库中的 [包解析器](../../packages/card-runtime/src/index.ts)、[ValueSchema](../../packages/card-runtime/src/schema.ts) 和 [受控组件渲染器](../../apps/web/src/extensions/ExtensionCardView.tsx)。修改示例前以这些实际代码为准。

## 先明确版本与验收范围

主示例使用 `formatVersion: "0.2"`。这是包格式版本，`version: "1.0.0"` 是卡片自己的内容版本，`host: "0.6"` 是宿主协议；三者含义不同。

2026-10-30后端v0.2服务接口已部署，真实模型一句话生成、安装、导出、启停和引用保护通过；当前线上静态页面仍只接受v0.1，实际加载模块的hash与下方快照一致。真实v0.2卡在旧页面显示“暂不可用”，原始数据保留。网页升级要求见[前端对接单](../design/FRONTEND-REQUESTS.md)，完整结果见[F阶段验收报告](../design/F-卡片包验收-20261030.md)。CLI和服务接口通过不代表网页可用。

另附 [fitness-log-v01](../../examples/vivicard/fitness-log-v01/manifest.json) 兼容包。它使用独立 ID `example.fitness-log-v01`，名称为“健身记录（0.1兼容）”，移除v0.2的新增元数据，保留相同的三个Schema、UI和实例示例。它已在旧展示页显示同一组真实生成的事实，但该测试仅验证显示，不证明旧网页支持v0.2，也不是v0.1自然语言生成验收。

两个示例二选一，只安装与宿主兼容的一个。它们用途相同，不要同时启用，以免争抢扩展契约选择。切换前先停用旧包；若已经安装了两者，先保证只启用一个，再处理不用的定义。仍被卡片引用的版本可以停用，不能直接删除。

## 前端快照的只读核对证据

核对对象为 [完整前端备份](../../deploy/online-snapshot/frontend-unified-background-20261029-1.zip)，不是对线上页面的操作。ZIP 的 SHA-256 与 [备份 README](../../deploy/online-snapshot/README.md) 一致：

```text
e42713d3eb58f86023028618aa0ec6cf453fb014200747a74bc283474ebc6690
```

归档通过 `manifest.json` 把 1,645 个逻辑文件映射到 405 个去重的 `objects/<sha256>` 内容对象。本次只在内存读取 manifest、入口 HTML 和少量相关 JS 对象，没有全量解压或修改任何静态资源。

入口 `web/index.html` 预加载 `assets/unified-background-20261029-1/src-BByP9_62.js`。该模块包含编译后的 manifest 解析函数 `oe`；它的对象路径和 SHA-256 为：

```text
objects/624a638c8815df2758d2b195958be3f6a53c48ab06d9ef3bce55bad6100bbdfb
```

实际对象内容已重新计算 SHA-256 与 manifest 对照。函数从 UTF-8 字节偏移 14219 开始，以下为其中原文：

```javascript
Y(e,[`formatVersion`,`id`,`version`,`name`,`description`,`renderer`,`host`,`capabilities`],t),
(e.formatVersion!==`0.1`||e.renderer!==`declarative`||e.host!==`0.6`)&&V(t,`仅支持 formatVersion 0.1 / declarative / host 0.6`);
```

因此该快照解析器确实仅支持 v0.1。白名单检查在版本条件之前：带 `examples`、`slots`、`icon`、`category` 的主包会先遇到 `manifest.json/<字段>: 不支持的字段`；即使移除新增字段而保留 `formatVersion: "0.2"`，仍会遇到上述“仅支持 formatVersion 0.1”报错。

同一发布目录的 `definitionStore-CIOvHtrM.js` 引用这个 runtime，并在安装、重新读取定义时重新校验。该依赖对象 SHA-256 为 `9cffd2cf8cd4931577f7e217690ff25fafeaf12a2866ba1416aae538144239b1`。这说明仅让服务端接受 v0.2，尚不足以证明旧前端能安装、重新加载或显示它。

前端集成需使用支持v0.2的共享card-runtime，保留新增元数据，一起验证导入、定义加载/重验、渲染和账号启用目录；服务接入按下文真实接口参数处理。本次仅在隔离评测账号只读观察线上页面和测试卡显示，未修改旧bundle。v0.1兼容包不能替代v0.2完整验收。

## 包的目录与五个核心文件

```text
examples/vivicard/fitness-log/
├── manifest.json
├── config.schema.json
├── data.schema.json
├── state.schema.json
├── ui.json
└── examples/
    └── default.json
```

五个核心 JSON 缺一不可，`examples/` 还必须有 1–12 个实例文件。每个实例严格包含 `name`、`config`、`data`、`state`。文件为 UTF-8 JSON，不支持注释和尾逗号。打包后的 ZIP 根目录直接包含 `manifest.json`，不能再套一层 `fitness-log/`。

包内只放协议 JSON；说明、生成脚本、截图和 `.vivicard` 产物放在包外。实例文件名使用英文字母、数字、下划线或连字符，例如 `examples/default.json`。压缩包至多 1 MiB、单文件至多 256 KiB、解压总量至多 1 MiB、文件数至多 32；路径、重复 JSON 字段和内容身份都会重新校验。

## manifest.json：元数据与模型参数

下面是主示例的完整 manifest。`capabilities` 必须是空数组；字段实际名是 `capabilities`，不是 `caps`。声明式包组合受控组件，不提供代码执行、外部服务或任意动作权限。

```json
{
  "formatVersion": "0.2",
  "id": "example.fitness-log",
  "version": "1.0.0",
  "name": "健身记录",
  "description": "记录用户明确提供的训练日期、训练部位和分钟数；相对日期由宿主结合当前日期及时区解析，缺少事实时询问，不复制DEMO数据。",
  "renderer": "declarative",
  "host": "0.6",
  "capabilities": [],
  "examples": [
    "今天练了40分钟背",
    "帮我记下昨天练腿30分钟",
    "记录今天胸部训练45分钟",
    "记一条肩部训练，今天20分钟",
    "今天练了60分钟全身"
  ],
  "slots": {
    "type": "object",
    "title": "训练事实",
    "description": "仅填写用户提供的训练事实；日期由宿主结合用户原话、当前日期及时区确认。",
    "additionalProperties": false,
    "properties": {
      "trainingDate": {
        "type": "string",
        "title": "训练日期",
        "description": "YYYY-MM-DD；宿主应校验真实日历日期并解析今天/昨天，不能采用示例日期。",
        "minLength": 10,
        "maxLength": 10
      },
      "bodyPart": {
        "type": "string",
        "title": "训练部位",
        "description": "依据用户原话规范化；无法确定时询问，不采用示例部位。",
        "enum": ["背", "腿", "胸", "肩", "手臂", "核心", "全身", "其他"]
      },
      "minutes": {
        "type": "integer",
        "title": "训练分钟数",
        "description": "用户明确给出的训练时长，1至600分钟；缺少时长时询问，不采用DEMO数值。",
        "minimum": 1,
        "maximum": 600
      }
    },
    "required": ["trainingDate", "bodyPart", "minutes"]
  },
  "icon": "💪",
  "category": "运动健康"
}
```

v0.2 新增字段都是可选的：

| 字段 | 含义与限制 |
| --- | --- |
| `examples` | 选择卡片时参考的触发话术；提供时为 3–10 条，每条 4–40 字，不含 URL。它们不是用户此次输入，也不授权执行其内容。 |
| `slots` | 一个根 `type: "object"` 的 ValueSchema，只约束扩展契约外层 slots 中的 `data` 部分；缺省时该部分使用 `dataSchema`。本示例与 dataSchema 完全一致，避免字段、必填项和值域漂移。外层始终是 `{config,data,state}`。 |
| `icon` | 至多 8 字符的图标文本；示例使用一个简单 emoji。不要放资源地址或代码。 |
| `category` | 至多 20 字符的分类文本。 |

ID 使用小写域式名称，最长 80 字符；卡片版本必须是 `x.y.z`。修改已安装包的任一内容，包括示例文件，都应增加卡片版本。同一 ID/版本却内容不同会冲突；安装后的实例通过 ID、版本和内容 hash 精确引用定义，hash 由工具和宿主生成。

服务端启用目录与 F3 的自动匹配约定是：同一个 ID 有多个已启用版本时，选择其中最高的 SemVer 作为新请求的匹配候选，按主版本、次版本、修订号的数值比较，例如 `1.10.0` 高于 `1.9.0`。已存卡片继续引用其原有的精确 `{id,version,hash}`，不会因高版本启用而自动迁移。

要让新请求回到旧版本，需停用所有高于目标版本且已启用的版本，并保持目标旧版本启用；停用不改变历史卡片的精确hash。这是自动匹配的版本选择规则，按hash读取/更新/导出的精确版本接口仍以显式身份为准。

该规则只合并同 ID 的版本候选，不会合并 `example.fitness-log` 和 `example.fitness-log-v01` 这两个不同 ID。两个健身包用途相同，仍只安装其中一个，避免同时启用后争抢匹配。

`manifest.examples` 是触发话术；`examples/default.json` 是完整的预览实例。这两类 examples 的用途不同，均不能作为新用户事实来源。

## config.schema.json：固定显示配置

```json
{
  "type": "object",
  "title": "显示配置",
  "description": "固定显示偏好，不包含训练事实。",
  "additionalProperties": false,
  "default": { "title": "训练记录" },
  "properties": {
    "title": { "type": "string", "title": "卡片标题", "default": "训练记录", "minLength": 1, "maxLength": 40 }
  },
  "required": ["title"]
}
```

`config` 保存标题等显示偏好。这里的“训练记录”是固定默认配置，可以用于创建新卡；它不是推断出来的训练事实。

## data.schema.json：必须有依据的训练事实

```json
{
  "type": "object",
  "title": "训练事实",
  "description": "仅填写用户提供的训练事实；日期由宿主结合用户原话、当前日期及时区确认。",
  "additionalProperties": false,
  "properties": {
    "trainingDate": {
      "type": "string",
      "title": "训练日期",
      "description": "YYYY-MM-DD；宿主应校验真实日历日期并解析今天/昨天，不能采用示例日期。",
      "minLength": 10,
      "maxLength": 10
    },
    "bodyPart": {
      "type": "string",
      "title": "训练部位",
      "description": "依据用户原话规范化；无法确定时询问，不采用示例部位。",
      "enum": ["背", "腿", "胸", "肩", "手臂", "核心", "全身", "其他"]
    },
    "minutes": {
      "type": "integer",
      "title": "训练分钟数",
      "description": "用户明确给出的训练时长，1至600分钟；缺少时长时询问，不采用DEMO数值。",
      "minimum": 1,
      "maximum": 600
    }
  },
  "required": ["trainingDate", "bodyPart", "minutes"]
}
```

训练日期、部位、分钟数没有 `default`。假设宿主已确认用户时区为 `Asia/Shanghai`、当前当地日期为 `2026-10-30`，用户说“今天练了40分钟背”，应填：

```json
{
  "config": { "title": "训练记录" },
  "data": { "trainingDate": "2026-10-30", "bodyPart": "背", "minutes": 40 },
  "state": { "note": "" }
}
```

这只是指定时钟条件下的期望实例。实际“今天”必须按宿主当次日期及时区解释；不能在包中硬编码今天，也不能填写示例的 `2026-01-15`、腿、25。用户只说“今天练背”时应询问分钟数，不能从触发话术中的 40 或实例中的 25 补值。用户只说“练了40分钟背”而没有可确定的日期时，应询问日期。部位无法可靠归类时也先询问。

Schema 的长度约束只能检查日期字符串有 10 个字符，不能证明它是合法日期。`YYYY-MM-DD` 在这里是说明文本；真正的日历日期和用户依据仍由宿主核对。

## ext.<id> 的实际 slots 与兼容形状

扩展契约的外层 slots 是 `{config,data,state}`；`manifest.slots` 只约束里面的 `data`。以本包为例，一条选卡后的契约条目可表示为下列形状；这不是上传包接口的 HTTP 请求体：

```json
{
  "contract": "ext.example.fitness-log",
  "slots": {
    "config": { "title": "训练记录" },
    "data": { "trainingDate": "2026-10-30", "bodyPart": "背", "minutes": 40 },
    "state": { "note": "" }
  }
}
```

外层 `config` 按 configSchema、`data` 按 `manifest.slots ?? dataSchema`、`state` 按 stateSchema 校验；最终实例还会通过三个实例 Schema 的校验。不要把 config/state 放进 manifest.slots，也不要把外层包装省略后当作推荐格式。

宿主兼容接受仅包含 data 字段的 flat slots，例如 `{trainingDate,bodyPart,minutes}`。只有 slots 完全不含 `config`、`data`、`state` 三个键时，才把它当 flat data，再用 `schemaDefaults(configSchema)`、`schemaDefaults(stateSchema)` 补充外层对象。已包装的 config/state 对象也只合并 Schema 显式默认值。不完整的混合包装不会被当作 flat data。

这些默认值仅能来自 Schema 的显式 `default`，不能从任何实例或 DEMO 的 config/data/state 复制生产字段。config/state 的必填字段若没有显式 default，仍需用户提供有依据的值；缺失就澄清，不能猜空字符串、0、false 或首个枚举值。即使数据部分已齐全，也不能绕过这些必填配置或状态。

生产出卡沿用现有 grounding：data 的日期、数字和 HTTP(S) 链接须有用户输入依据；config/state 的相应值只能依据用户输入或 Schema 显式默认。包内实例、触发话术和“通过 Schema”本身均不是用户事实证据。该逻辑见 [slotPlanner](../../apps/local-api/src/intent/slotPlanner.ts) 与 [扩展场景构建](../../apps/local-api/src/scenes/extensions.ts)。

## state.schema.json：个人备注

```json
{
  "type": "object",
  "title": "个人状态",
  "description": "用户后续可编辑的备注，默认空字符串，不推断训练强度或感受。",
  "additionalProperties": false,
  "default": { "note": "" },
  "properties": {
    "note": { "type": "string", "title": "备注", "default": "", "maxLength": 120 }
  },
  "required": ["note"]
}
```

Schema 字段名为 `default`，运行时辅助函数叫 `schemaDefaults(schema)`，没有 `defaults` 这个 Schema 关键字。宿主读取显式默认值、组成 `config/data/state` 后再校验；校验器本身不会自动填充缺失字段。本包生产初值来自 configSchema 和 stateSchema 的显式 `default`，不会从实例的 config/data/state 读取任何生产字段。无显式默认的必填配置或状态须有用户依据，否则澄清。

## ui.json：只绑定已声明字段

```json
{
  "components": [
    { "component": "Header", "bind": "/config/title" },
    { "component": "KeyValue", "label": "训练日期", "bind": "/data/trainingDate" },
    { "component": "Badge", "label": "训练部位", "bind": "/data/bodyPart" },
    { "component": "Metric", "label": "训练时长（分钟）", "bind": "/data/minutes" },
    { "component": "KeyValue", "label": "备注", "bind": "/state/note" }
  ]
}
```

UI 是 1–30 个纵向排列的受控组件。每项只允许 `component`、可选 `label`、`text`、`bind` 和 Table 专用 `columns`。`text` 与 `bind` 必须二选一；label 最长 120，固定 text 最长 400。

| 组件 | 绑定类型与实际含义 |
| --- | --- |
| `Header` | 字符串、数字、整数或布尔值；作为标题显示。 |
| `KeyValue` | 基础值；显示 label 与值。 |
| `Metric` | 基础值；大字号显示数字或文本，不自行计算。 |
| `List` | 数组；逐项展示，空数组显示占位。 |
| `Image` | 字符串；实际显示仅接受不含用户名/密码的 HTTPS 图片地址。DEMO 预览不加载远程图片。 |
| `Badge` | 基础值；显示徽标，可带 label。 |
| `Link` | 字符串；实际打开仅接受不含用户名/密码的 HTTPS 地址。DEMO 中不会打开链接。 |
| `Table` | 对象数组；必须有 `columns: [{"label":"列名","field":"字段名"}]`，1–8 列，field 是 items.properties 中的直接字段名。 |
| `Progress` | number/integer；按 0–100 的百分比显示，建议 Schema 同时声明该值域。传入 40 显示 40%，不会根据分钟数自动换算。 |

`bind` 是 JSON Pointer，根只允许 `/config`、`/data`、`/state`，路径必须在对应 Schema 中声明。嵌套对象可用 `/data/session/minutes`，数组首项可用 `/data/sessions/0/minutes`；两者必须先有相应对象/数组 Schema。JSON Pointer 的 `~1` 表示 `/`、`~0` 表示 `~`，但当前 Schema 字段名受限，本示例无需转义。

下面这些写法没有求值能力：`data.minutes`、`/data/minutes * 2`、`${data.minutes}`、`/data/minutes + '分钟'`。需要单位时像示例一样放在 label 中。组件不能带 React、HTML、CSS、事件处理器或任意表达式。Table 的 `field` 也不是 Pointer 或表达式。

{
  "name": "DEMO：虚构的腿部训练25分钟",
  "config": { "title": "训练记录" },
  "data": { "trainingDate": "2026-01-15", "bodyPart": "腿", "minutes": 25 },

## ValueSchema 允许什么

每个节点必须显式声明 `type`；config、data、state、manifest.slots 的根均为 object。所有 object 必须有 `properties` 和 `additionalProperties: false`，每层至多 64 字段。字段名使用英文字母开头的英文字母、数字、下划线、连字符，最长 64；不能使用原型相关名称。

| 适用范围 | 允许的关键字 |
| --- | --- |
| 通用 | `type`、`title`、`description`、`default`；基础值可用 `enum`。 |
| `object` | `properties`、`required`、`additionalProperties: false`。 |
| `array` | `items`、`minItems`、`maxItems`。 |
| `string` | `minLength`、`maxLength`。 |
| `number` / `integer` | `minimum`、`maximum`。 |
| `boolean` | 无额外类型关键字。 |

`title`/`description` 最长 400；enum 为 1–50 个与类型一致的基础值；数组最多 200 项；字符串最多 10000 字符；Schema 嵌套最多 10 层。`default` 本身也必须通过对应 Schema。当前字符串长度以运行时字符串单位为准，含 emoji 时不要靠目测贴着字符上限填写。

不支持 `pattern`、`format`、`$ref`、`$schema`、`$defs`、`oneOf`、`anyOf`、`allOf`、`const`、`if/then/else`、`nullable`、`minProperties` 等额外关键字。不能把完整 JSON Schema 模板直接贴进来；未知关键字会报错，而不是悄悄忽略。

## 实际自检与打包

在包含根 `package.json` 的 Vivic 仓库目录执行。根脚本已按 `INIT_CWD` 解析路径，下面的相对路径都以启动命令的目录为准；也可传绝对路径。

本机若能运行 `corepack pnpm --version`，但下列命令报“pnpm is not recognized”，是根脚本内部的 `pnpm` 不在 PATH。Windows 的本次验证使用现有 Corepack shims 临时补充当前终端 PATH，没有更改项目或全局配置：

```powershell
$taskNodeDir = Split-Path (Get-Command node.exe).Source
$taskCorepackShims = Join-Path $taskNodeDir 'node_modules/corepack/shims'
if (!(Test-Path -LiteralPath (Join-Path $taskCorepackShims 'pnpm.cmd'))) {
  throw '请先定位本机已有的 Corepack shims 目录，再加入当前终端 PATH。'
}
$env:Path = $taskCorepackShims + [System.IO.Path]::PathSeparator + $env:Path
```

```powershell
corepack pnpm card:check examples/vivicard/fitness-log
corepack pnpm card:pack examples/vivicard/fitness-log ../delivery/vivicard-fitness-log-20261030/fitness-log-v02.vivicard
corepack pnpm card:check ../delivery/vivicard-fitness-log-20261030/fitness-log-v02.vivicard
```

成功输出包含 `valid: true`、ID、版本、hash、实例数量；pack 会先校验目录，再校验 ZIP 内容身份。输出文件已存在时会拒绝覆盖，改用新的文件名即可。不要用改扩展名的普通 JSON 冒充包，也不要把打包产物放进包源码目录。

如果不调整PATH，也可从仓库根目录直接调用；以下命令已在本机验证。目标目录仍相对仓库根目录，不要再加`../../`：

```powershell
corepack pnpm --filter @vivic/local-api exec tsx ../../packages/card-runtime/src/cli.ts examples/vivicard/fitness-log
corepack pnpm --filter @vivic/local-api exec tsx ../../packages/card-runtime/src/pack.ts examples/vivicard/fitness-log ../delivery/fitness-log-new.vivicard
corepack pnpm --filter @vivic/local-api exec tsx ../../packages/card-runtime/src/cli.ts ../delivery/fitness-log-new.vivicard
```

需要兼容候选时，单独校验和打包：

```powershell
corepack pnpm card:check examples/vivicard/fitness-log-v01
corepack pnpm card:pack examples/vivicard/fitness-log-v01 ../delivery/vivicard-fitness-log-20261030/fitness-log-v01.vivicard
corepack pnpm card:check ../delivery/vivicard-fitness-log-20261030/fitness-log-v01.vivicard
```

如果v0.2主包遇到“仅支持0.1”或manifest新字段不支持，请先核对本机运行时版本，使用本分支支持v0.2的运行时再跑。保留v0.2主包，不为迁就旧解析器悄悄删掉其元数据；兼容包单独保留身份。

目录/ZIP 检查只能证明包结构、绑定和示例合法。它不会调用模型，不验证自然语言准确率，也不证明日期日历有效、数字来自用户或 UI 已兼容。

## 托管卡片包 API：按账号的真实接口

以下参数以[hosted/cardPackages.ts](../../apps/local-api/src/hosted/cardPackages.ts)为准，服务端已随3b91986上线。接口使用已登录、有效设备的Cookie身份，按当前账号隔离。写请求要求同源Origin；接口不接受Authorization头，也不是API Key上传通道。

| 操作 | 实参和结果 |
| --- | --- |
| `GET /api/space/cards` | 不带查询参数；返回 `{definitions:[{key,definition,enabled}]}`。 |
| `POST /api/space/cards` | `multipart/form-data`：恰好一个 `file`，文件名以 `.vivicard` 结尾且大小为 1–1048576 字节；可选一个 `enabled`，字符串 `"true"` 或 `"false"`。不接受 JSON definition、其他表单字段或查询参数。返回 `{ok:true,record}`，同内容重装可带 `deduplicated:true`。 |
| `PATCH /api/space/cards/:id` | JSON `{enabled:boolean,hash?:string}`，也可用 `?hash=<64位小写hex>` 指定版本；两处都给时必须一致。返回 `{ok:true,record}`。 |
| `DELETE /api/space/cards/:id?hash=<hash>` | 必须给明确 hash；删除精确版本，返回 `{ok:true}`。该账号任一 Space 仍有卡片引用时返回冲突，可先停用。 |
| `GET /api/space/cards/:id/package?hash=<hash>` | 导出原定义的标准 ZIP `.vivicard`；导出内容重新检查 hash。 |

上传时未指定 enabled 的新包默认启用；同一内容重装保留此前启用状态，不用 POST 重装来切换状态，改用 PATCH。单个 ID 有多个版本时，读取/更新/导出需明确 hash，否则会报歧义；建议这些操作始终给 hash。除表中 hash 外，单包接口不接受其他查询参数；删除始终要求 hash。

每账号最多安装 32 个定义、启用 16 个定义。服务端完整重验 ZIP、原始文件和 hash。安装、启用或列表响应中的定义不能由客户端自行宣布可信。

模型选择和执行目录只使用服务端读取的本账号已启用包：`readEnabledCardDefinitions(store, accountId)`，通过托管 session 的 `getEnabledDefinitions` 注入。客户端随 intent 提交的 defs 或本地缓存不能成为授权来源。安装候选后还需确认它实际处于此账号启用目录，且不要同时启用两个健身示例。旧 `/api/space/owner/definitions` 是兼容同步入口，不等同于上述 multipart 上传接口；这里不把两者的请求体混用。
