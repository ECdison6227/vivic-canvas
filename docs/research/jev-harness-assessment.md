## 可应用的部分（设计推断，尚未验证）

Vivic 可以先定义有限的候选卡片、操作和当前状态，由决策模型判断路由、目标候选或是否需要澄清；开放式内容生成仍交给 LLM。程序核对 Schema、目标和允许操作后执行。

TianyuCodings 方案中“开发时形成并固定流程、运行时调用决策模型”的方式值得验证。候选复用点包括问题组织、结构化判断、固定流程版本与轨迹回放；其 Python/表达式执行和自动改写 harness 的能力不能直接进入现有 Vivic 产品运行链路。开发工具生成的流程也须经过审查、固定和测试后才能作为正常应用代码交付。

TypeSafeAI 方案可参考提案验证与审查记录，但不能引入 `read_file`、`propose_patch` 或把其 `permit` 结果当成执行授权。将问题换成卡片/数据操作语义需要重新评估，原问题集和阈值不能直接照搬。

API 与本地应走统一的 Vivic 决策适配接口；“harness 开源”不证明远端模型权重开源，也不证明能在用户本地运行。现有 Kev 固定版本与候选框架的协议兼容性、Windows 能力和准确率仍需独立验证。

## L04 的进入与验收

1. 确认目标仓库、版本与许可证，核对依赖、输入输出和真实模型适配。
2. 用 Vivic 的中文命令、否定/复合句、歧义目标与候选卡片做离线对照，保留现有规则/LLM 基线；不以“高置信度”替代实际正确率。
3. 实现 API/本地统一接口，逐条验证实际支持的路径、取消、超时、断连与恢复；记录端到端延迟和调用成本。
4. 产品默认引导接入，在连接可用时优先使用；用户显式关闭可持久化。临时故障或判断不确定走明确降级，不静默永久关停、不阻断基础文字使用。
5. 只在效果与维护成本有依据时选择复用范围。决策层涉及核心流程，由维护者牵头；稳定接口下的独立适配、评测或界面可另行分配，不因此扩大任何已有任务的范围。
