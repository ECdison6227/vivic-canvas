# 模型连接稳定性（2026-10-17）

## 问题

用户反馈 StepFun API Key 和 GPT 连接都「非常不稳定」。本机实测（Windows，系统代理 FlyingBird `127.0.0.1:7892`）：

| 现象 | 实测 | 原因 |
| --- | --- | --- |
| GPT 请求时好时坏 | 经代理的新隧道 TLS 握手 3.5–9.5 秒；8 次里 2 次 `UND_ERR_CONNECT_TIMEOUT`（10.7 秒） | undici 默认握手上限 10 秒，正好卡在边界 |
| GPT 每次都慢 | 每次推理约 9 秒，其中约 4.6–9 秒是重建隧道 | undici 空闲 4 秒就关连接，两次指令之间隧道必然被丢弃 |
| GPT 约每小时失败一次，提示「授权可能已被撤销或过期，请重新登录」 | 连接时刷新令牌 15.3 秒后失败；随后同一刷新令牌直接刷新成功（11.4 秒） | Pi 的 OAuth 刷新硬编码 15 秒超时，冷隧道握手就占 9–10 秒；超时被误报为授权失效。刷新若在 OpenAI 轮换令牌后才超时，唯一有效的刷新令牌会丢失 |
| GPT 连接验证失败 | 刷新令牌 + 模型目录 + 推理探测串行，冷启动 14–22 秒 | 总时限只有 20 秒 |
| 一次网络抖动就报错 | 推理遇到断连、429、5xx 直接失败；断连还被误标为「未返回可验证的 JSON」 | 推理请求从不重试 |
| StepFun 连接测试偶发失败 | 探测只给 256 token；`step-3.5-flash` 推理模型可能把额度全用在思考上、正文为空 | 探测要求返回 JSON，否则判定连接失败；总时限 12 秒 |
| StepFun 指令偶发失败 | 断连、429、5xx 不重试；推理单次 45 秒上限 | — |
| 「刚才还连着，突然未连接」 | 开发后端 `tsx watch` 每次源码改动都会重启；StepFun Key 只在内存，GPT 连接与所选模型也都在内存 | 重启后静默回到「StepFun · 未连接」 |

StepFun 直连本身很稳（`api.stepfun.com` 12–108 ms，无失败）。

## 修改

**GPT 代理出口**（`openaiProxy.ts`）：隧道 TLS 握手上限 30 秒；空闲保活 5 分钟（实测代理在 90–150 秒空闲后关闭隧道，undici 会干净重建，不报错）。Control 页面打开且所选为 GPT 时，状态轮询每 60 秒向推理主机发一次**不带凭据**的 HEAD，让隧道保持可复用。页面关掉即停止。

**GPT 令牌刷新**（`gpt/provider.ts`）：包装 Pi 的 OpenAI/Codex OAuth `refresh`，把它收到的 15 秒超时换成 60 秒，刷新实现本身不变。保温时顺带调用一次 `getAuth`，令牌临近过期（剩余不足 5 分钟）时在后台提前刷新，用户指令不再承担刷新耗时。刷新超时提示改为「已保存的授权没有失效，请稍后重试，无需重新登录」。

**重试策略（两家一致）**：断连、无响应、429/408/409/425/5xx、或 HTTP 200 但流中途断开，在**同一时限内只重试一次**（间隔 0.8 秒；StepFun 遵守不超过 5 秒的 `Retry-After`）。401/403/400 等拒绝、超时、非 JSON 输出不在这里重试（非 JSON 仍由规划器原有的一次修复处理）。此前「推理绝不自动重发」的测试已按新策略改写。

**时限**：GPT 连接验证 20 → 60 秒，单次推理 45 → 60 秒；StepFun 连接测试 12 → 30 秒，单次推理 45 → 60 秒。整轮指令仍受 90 秒上限约束，前端 100 秒；前端连接请求等待 25 → 75 秒。

**StepFun 连接测试**：推理探测只要返回 HTTP 200 的生成结果即通过（证明 Key 有 Plan 推理权限），不再因正文为空或不是 JSON 判失败；模型目录遇到断连或 5xx 重试一次，401 不重试。模型输出兼容 ```` ```json ```` 代码块包裹；正文为空且 `finish_reason=length` 时提示「模型思考用尽了输出长度」。

**重启后恢复**（`preferences.ts`）：所选模型（StepFun/GPT）、GPT 登录来源（Pi/Vivic）和 GPT 模型名保存在 `~/.vivic/preferences.json`（只有名称，没有任何 Key 或令牌）。后端启动时自动用已有授权恢复 GPT；恢复期间面板显示「正在恢复 GPT 连接…」，此时到达的指令会等待恢复完成。点「断开 GPT」会清除记录，不再自动恢复。StepFun Key 仍只在内存，**重启后必须重新输入**；面板会明确提示「本地服务刚刚重启…已随重启清除」，而不是只显示「未连接」。

Playwright 后端设置 `VIVIC_PREFERENCES=off`，不会读写用户的真实偏好，也不会自动连接用户的 GPT；单元测试不注入偏好存储。

## 实测对比（同一台机器、同一代理、真实 ChatGPT 授权）

| | 修复前 | 修复后 |
| --- | --- | --- |
| 间隔 8–20 秒的推理 | 8.8–9.4 秒/次，每次重建隧道 | 3.0–4.3 秒/次，复用隧道（4/4 成功） |
| 隧道空闲 20/45/90 秒后的请求 | 重建，3.5–9.5 秒，可能 10 秒超时 | 复用，0.3–0.5 秒 |
| GPT 连接验证 | 9–14 秒，冷启动可超 20 秒判失败 | 9.5–14 秒，上限 60 秒 |
| 令牌临近过期时连接 | 15.3 秒超时失败，提示重新登录 | 刷新上限 60 秒；实测刷新 11.4 秒成功 |
| 经 5177/8790 的真实规划指令（间隔 20 秒） | — | 3/3 成功，3.3–4.7 秒 |
| 后端重启后立即发指令（所选为 GPT） | 立即返回「GPT 未连接」 | 等待自动恢复后正常返回结果（26 秒，含冷启动） |

StepFun 侧没有可用的 Key，未做真实推理对比；网络直连已实测稳定，改动由单元测试覆盖（重试次数、Retry-After、空正文探测、代码块 JSON、目录重试）。

## 仍需注意

- 代理节点本身慢（单次握手 9 秒）时，空闲超过约 2 分钟后的首个请求仍要多等约 10 秒，但不再因 10 秒上限失败。
- 日常使用建议用 `pnpm --filter @vivic/local-api start`（不监听文件），避免源码改动触发重启清掉 StepFun Key。
